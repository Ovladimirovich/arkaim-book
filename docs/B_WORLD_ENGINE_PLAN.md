## Простыми словами

Фаза A сделала так, чтобы Arkaim помнил диалог и маршруты (Ask → история → World → Temporal).
Фаза B делает **World** самостоятельным исследовательским пространством: пользователь должен
мочь взять сущность, увидеть все её связи, перейти по любой связи к другой сущности и не
потерять нить расследования.

## Что уже есть (проверено по коду, ничего не выдумывается)

Backend (`runtime/core/routes/world_engine.py`, prefix `/world`, на фронте `/book/world/*`):

| Контракт | Что отдаёт |
|---|---|
| `GET /world/summary` | stats: количество сущностей/категорий |
| `POST /world/search` | `world_model[]` + `relations[]` |
| `GET /world/entity/{id}` | одна сущность (404, если нет) |
| `GET /world/entity/{id}/context` | `entity`, `relations{outgoing_count, incoming_count, outgoing[]}` |
| `GET /world/entity/{id}/visual-prompt` | визуальный промпт |
| `GET /world/categories`, `/rules`, `/modes`, `/form-library` | справочники мира |
| `GET /temporal/chain`, `/temporal/context/{epoch}` | реальная временная цепочка с `entity_ids` |
| `GET /knowledge/...` (`routes/knowledge_cards.py`) | карточки знаний, поиск сущностей |
| `services/related_entities.py` | детерминированный подбор сущностей под ответ диалога |

Что фронтенд **не делает** сейчас (пробелы, которые закрывает фаза B):

1. В карточке контекста сущности показано только **5 исходящих** связей и **вообще не показаны входящие** (счётчик есть, список — нет).
2. Связи не кликабельны: перехода `сущность → связанная сущность` нет.
3. Нет навигации «назад по следу расследования» — каждая загрузка сущности затирает предыдущую.
4. События/эпохи, связанные с сущностью, показываются только кнопкой «Временной контекст →», без данных прямо в карточке.

## Задачи фазы B

### B1 — Полная карточка связей сущности и переходы по связям (первая задача)
- Показать **все** исходящие и **все** входящие связи с типами (без обрезки до 5).
- Каждая связь — кликабельный переход: загружает контекст целевой сущности и обновляет `?entity_id=` в URL.
- Пустые состояния: «связей нет» — честно, без выдумок.
- **Критерии приёмки:** `tsc` 0 ошибок, ESLint 0 ошибок, unit-тесты зелёные, smoke в браузере: открыть сущность → перейти по связи → открылась вторая сущность → URL содержит её `entity_id`.

### B2 — След расследования (навигация World)
- Стек «посещённые сущности» / кнопка «назад по следу» без потери контекста.
- Сохранение выбранной сущности и поискового запроса в URL (поиск тоже).
- **Критерии:** переходы работают, refresh ничего не теряет.

### B3 — События и эпохи сущности прямо в World
- В карточке сущности показать реальные связанные эпохи/события из `temporal` (там, где `entity_ids` реально содержат сущность).
- Переход `сущность → эпоха → обратно к сущности`.
- **Критерии:** данные только из реальных контрактов; при отсутствии связей — честная подсказка (как сейчас на `/temporal`).

### B4 — Источники в World (переходит в фазу D, если backend не готов)
- Определить, отдаёт ли backend provenance для сущностей. Если да — показать «откуда известно». Если нет — зафиксировать как задачу фазы D и не выдумывать.

## Риски

- Список входящих связей может быть большим (547 сущностей, 287 связей) — нужна пагинация/ограничение и счётчики.
- Связи в `outgoing[]` отдаются без имён целевых сущностей (только `target_id`) — потребуется разрешение имён через `GET /world/entity/{id}` или поиск; если это дорого, показываем `target_id` как сейчас, но кликабельным.
- Playwright e2e не прогоняются в этой итерации (требуют полной инфраструктуры) — рискуем задеть существующие `world-temporal.spec`; проверка — обязательный smoke + существующие unit.
