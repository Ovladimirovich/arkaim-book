# A1_ROUTE_STATE_MAP_REPORT.md — карта состояния маршрута

**Статус:** DOCUMENTED

**Режим:** исследование существующей реализации; код не изменялся  
**Проверенный маршрут:** `Ask → Answer → Entity → World → Temporal → History`

## 1. Краткий результат

Маршрут в текущем frontend уже имеет рабочие вертикальные переходы и deep links для основных страниц. Но единого состояния маршрута нет: параметры сессии и сущности передаются между страницами непоследовательно, а ответ Ask не восстанавливается после перезагрузки.

Главный пользовательский риск: пользователь может уйти из Ask в World/Temporal, вернуться или обновить страницу и потерять часть контекста исследования.

## 2. Карта фактических переходов

| Переход | Что происходит сейчас | Состояние передаётся | Где теряется или ограничено |
|---|---|---|---|
| Ask → Answer | Вопрос отправляется в `/v1/stream`; при не-SSE используется `/book/ask`. Ответ добавляется в локальный `messages`. | `session_id` | После F5 `messages` не загружаются заново; сессия остаётся, видимый диалог исчезает. |
| Answer → Entity | `related_entities` рендерятся через `EntityCard`. | `entity_id`, `session_id` | Связь карточки с конкретным сообщением есть только в текущем React-состоянии. |
| Entity → World | Переход на `/world-engine?entity_id=...&session=...`. | `entity_id`, `session_id` | `session` передаётся дальше только при переходе в Temporal; World сам его не использует и не показывает. |
| World → Entity context | Загружается `/book/world/entity/{id}/context`. | URL `entity_id` при первом входе | После выбора другой сущности URL не обновляется; F5 может открыть исходный deep link, а не последнюю выбранную сущность. |
| World → Temporal | Переход на `/temporal?entity=...&session=...`. | `entity_id` как `entity`, `session` | Переход доступен на карточке независимо от наличия подтверждённой связи; backend может показать полную цепочку без связи. |
| Temporal → World | Кнопка «Открыть в World» строит `/world-engine?entity_id=...&session=...`. | `entity_id`, `session_id` | Сохраняется только исходная сущность; выбранная эпоха не включается в deep link. |
| Temporal → Ask | Кнопка «К диалогу» делает `router.push('/ask')`. | Ничего | Теряются `entity_id`, `session_id`, выбранная эпоха и контекст диалога. |
| History → conversation | Выбор сессии загружает `/book/reader/history/full?session_id=...`. | `session_id` внутри React-состояния | После F5 выбранная сессия не восстанавливается из URL. |
| Conversation → World | Перехода из сообщения истории к связанной сущности нет. | Нет | История показывает текст и дату, но не продолжает исследовательский маршрут. |
| World/Temporal → Ask | Прямой общей кнопки с сохранением контекста нет. | Только косвенно и частично | Нужна отдельная карта origin/session/selected context. |

## 3. Что уже работает

1. `arkaim_session_id` создаётся и сохраняется в `localStorage` в Ask.
2. `session_id` передаётся в SSE metadata и fallback `/book/ask`.
3. Ask получает `related_entities` и строит `EntityCard` с deep link в World.
4. World поддерживает начальный deep link `entity_id` и загружает реальный context API.
5. World передаёт `session` в Temporal, если параметр присутствует.
6. Temporal использует только реальные узлы `getTemporalChain()` и не создаёт mock-цепочку.
7. Temporal показывает явное предупреждение, если backend не подтвердил связь выбранной сущности с эпохой.
8. History загружает реальные данные ReaderMemory и показывает ошибку вместо фиктивного диалога.
9. History умеет открыть конкретную сессию и повторно загрузить данные.

## 4. Точки потери состояния

### P0 — Ask не восстанавливает сообщения после reload

- `sessionId` восстанавливается из `localStorage`.
- `messages` инициализируются пустым массивом.
- При переходе обратно в `/ask` или F5 диалог не запрашивается из `/book/reader/history/full`.
- В результате существующая backend-сессия визуально не связана с её сообщениями.

**Следствие:** нарушается главный критерий Core Flow — продолжение разговора после перезагрузки.

### P1 — EntityCard показывает недоступное действие как доступное

- Кнопка «Временной контекст» рендерится для любой `RelatedEntity`.
- Payload не содержит признака подтверждённой временной связи.
- Temporal затем честно сообщает, что связи в backend нет, и показывает полную цепочку.

**Следствие:** интерфейс предлагает исследовательский переход, который может не привести к контексту именно выбранной сущности. Это не ложный факт, но UX не отражает доступность связи.

### P1 — World не нормализует состояние в URL

- `selectedEntity` и `entityContext` живут в React-состоянии.
- При ручном выборе сущности URL остаётся прежним.
- При F5 восстанавливается только `entity_id` из первоначального URL.
- Внутренние переходы между найденными сущностями отсутствуют: связи показаны текстом `target_id`, но не кликабельны.

### P1 — Возврат из Temporal в Ask теряет весь контекст

- Кнопка «К диалогу» жёстко переходит на `/ask`.
- `session`, `entity` и выбранный epoch не включаются в переход.
- На Ask нет механизма принять выбранную сущность как активный контекст будущего вопроса.

### P1 — History не завершает исследовательский маршрут

- История отображает сообщения, но не показывает `related_entities` из metadata.
- Нет перехода из ответа/сообщения в World или Temporal.
- Нет URL-параметра для выбранной сессии, поэтому состояние фильтра теряется после F5.

### P2 — Источник ответа не всегда отображается

- SSE-ветка всегда записывает `sourceType: 'hybrid'`, даже если SSE не прислал источник.
- Fallback-ветка вычисляет `sourceType` из строки `source`.
- В history metadata источник и связанные сущности не нормализованы для отображения.

### P2 — Ошибка Ask маскируется как mock-сообщение

- В `catch` создаётся сообщение с `sourceType: 'mock'`.
- Пользователь видит текст ошибки, но mock-статус не объясняет, что это не ответ книги и не результат Knowledge.

## 5. Текущие источники состояния

| Состояние | Источник | Владелец | Надёжность |
|---|---|---|---|
| Auth session | HTTP-only cookie | Backend auth | Сохраняется при переходах/F5 по имеющимся проверкам. |
| Ask `session_id` | `localStorage.arkaim_session_id` | Ask frontend + ReaderMemory backend | Сохраняется, но не является URL-состоянием. |
| Ask `messages` | локальный React state | Только Ask frontend | Теряется при reload. |
| `related_entities` | SSE или fallback response | Backend response | Теряется после reload, пока история не восстановлена. |
| World selected entity | локальный React state | Только World frontend | Теряется при reload/clientside selection. |
| World `entity_id` | URL query | Navigation | Восстанавливается только исходный URL. |
| Temporal `entity` | URL query | Navigation | Восстанавливается при reload. |
| Temporal `epoch` | URL query, если передан | Navigation | В `TemporalContent` есть начальное значение, но UI не обновляет URL при выборе. |
| Temporal selected epoch | локальный React state | Только Temporal frontend | Теряется как URL deep link; начальное значение не гарантирует актуальный URL. |
| History selected session | локальный React state | Только History frontend | Теряется при reload. |
| ReaderMemory | backend SQLite/API | Backend | Реальный источник persistence для сообщений. |

## 6. Предлагаемая целевая карта состояния A1

Это ещё не реализация и не новая задача. Это минимальная схема, которую нужно согласовать перед A2.

```text
Origin:
  source = ask | history | world | temporal | reading
  session_id = ...
  entity_id = ...
  selected_epoch = ...
```

Правила:

1. `session_id` должен сохраняться при переходах Ask → Entity → World → Temporal → Ask.
2. `entity_id` должен быть URL-параметром в World и Temporal.
3. `selected_epoch` должен стать URL-параметром Temporal при выборе эпохи, если это нужно для восстановления.
4. `origin` нужен только для объяснения возврата и не должен становиться источником фактов.
5. При возврате в Ask должен быть виден выбранный контекст либо пользователь должен иметь явный способ сбросить его.
6. Состояние `messages` должно восстанавливаться из ReaderMemory по `session_id`, но это отдельная задача A1/A2-реализации после согласования контракта.
7. History должен иметь deep link на сессию, чтобы восстановить выбранный разговор.

## 7. Правильная последовательность следующих задач

A1R не следует начинать как задачу на исправление UI. Сначала владелец должен утвердить контракт состояния, затем задачи выполняются строго по порядку:

1. **A1R — контракт состояния маршрута**
   - определить единый контракт `session_id / entity_id / epoch / origin`;
   - определить правила URL, Back и Refresh;
   - определить источник истины для каждого состояния;
   - **без реализации UI**.

2. **A2 — восстановление Ask из ReaderMemory**
   - после F5 восстановить сообщения текущей сессии;
   - открыть `/ask?session_id=...`;
   - проверить Refresh и Back.

3. **A3 — синхронизация World с URL**
   - выбранная сущность отражается в URL;
   - deep link открывает именно её;
   - Back/Forward работают предсказуемо.

4. **A4 — сохранение контекста Temporal**
   - сохранять `session_id + entity + epoch`;
   - переходы Temporal ↔ Ask/World не теряют контекст.

5. **A5 — History deep links**
   - выбранная сессия отражается в URL;
   - из History можно продолжить исследование без потери контекста.

6. **A6 — корректность состояний и ошибок**
   - убрать ложный `hybrid`;
   - убрать misleading `mock` для реальной ошибки;
   - показывать Temporal только при подтверждённой связи.

Каждая задача требует отдельного `OWNER-GO`. A1R не начинается автоматически после A1.
