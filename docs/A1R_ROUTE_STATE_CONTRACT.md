# A1R_ROUTE_STATE_CONTRACT.md — контракт состояния маршрута

**Статус:** DOCUMENTED  
**Задача:** A1R — контракт состояния маршрута  
**Режим:** проектирование контракта; UI и код продукта не изменялись  
**Основание:** A1 — `docs/A1_ROUTE_STATE_MAP_REPORT.md`

---

## 1. Цель контракта

Единый маршрут должен сохранять исследовательский контекст при переходах между страницами, не подменяя источник истины и не создавая неподтверждённые связи:

```text
Ask → Answer → Entity → World → Temporal → History
```

A1R определяет, **что передаётся, где это хранится и кто является источником истины**. Он не реализует форму, компоненты, API или восстановление сообщений.

## 2. Минимальная модель состояния

```ts
type RouteState = {
  session_id: string | null;
  entity_id: string | null;
  epoch_id: string | null;
  origin: 'ask' | 'history' | 'world' | 'temporal' | 'reading' | null;
};
```

### 2.1. `session_id`

**Назначение:** идентифицирует одну сессию диалога и связывает Ask с ReaderMemory.

**Правила:**

- Ask должен использовать один стабильный `session_id` для всех вопросов сессии.
- Значение передаётся в `/book/ask` и `/v1/stream` как `session_id`.
- Значение передаётся в deep links Ask, World и Temporal.
- Значение не является идентификатором сущности, эпохи или источника истины.
- При отсутствии значения frontend не должен изобретать фиктивную серверную сессию для восстановления истории; Ask может создать новую сессию только по действующему правилу создания новой сессии.

**Источник истины:** backend ReaderMemory для содержимого истории; `session_id` сам по себе является идентификатором, а не доказательством существования сообщений.

**Важное ограничение:** текущий `reader.ts` документирует архитектурный факт: `/book/reader/history` может читать таблицу, которую `/book/ask` не заполняет. Поэтому A1R фиксирует контракт, но A2 обязан сначала подтвердить фактический persistence для выбранного Ask endpoint и не обещать восстановление пустого диалога.

### 2.2. `entity_id`

**Назначение:** выбранная каноническая сущность World.

**Правила:**

- Ask → EntityCard передаёт `entity_id` из `related_entities`.
- World принимает `entity_id` из URL и загружает соответствующий backend context.
- Выбор другой сущности в World обязан отражаться в URL; это реализация A3, а не часть A1R.
- Temporal использует тот же идентификатор в query-параметре `entity`.
- Значение не подтверждает существование временной или иной связи: Temporal должен проверить `entity_ids` в ответе backend.

**Источник истины:** backend World/Knowledge context. Отсутствие сущности — отдельный результат, не повод создавать карточку на frontend.

### 2.3. `epoch_id`

**Назначение:** выбранный узел временной модели для восстановления Temporal-контекста.

**Правила:**

- Идентификатор берётся из `TemporalNode.era_id` либо другого backend-подтверждённого идентификатора узла.
- Значение передаётся в URL Temporal при выборе узла; это реализация A4.
- Значение не вычисляется из названия, порядка или догадки.
- Неизвестная дата остаётся неопределённой; `epoch_id` не должен подменяться случайным ID.
- Context загружается только через подтверждённый endpoint `/book/temporal/context/{epoch_id}`.

**Источник истины:** backend Temporal `nodes`, `relations`, `provenance` и `context`; frontend не синтезирует цепочку и даты.

### 2.4. `origin`

**Назначение:** технически объяснить, откуда пользователь пришёл и куда предложить возврат.

**Допустимые значения:** `ask`, `history`, `world`, `temporal`, `reading`.

**Правила:**

- `origin` не является доказательством, разрешением или источником факта.
- Он не должен использоваться для формирования Knowledge.
- Значение должно быть нормализовано и иметь fallback на текущую страницу.
- `origin` не должен бесконечно переходить сам в себя; при цикле сохраняется последний валидный origin.

## 3. URL-контракт

### 3.1. Ask

```text
/ask?session_id=<session_id>
```

Обязательные правила:

- `session_id` — единственный параметр, необходимый для идентификации диалога.
- При переходе из другой страницы Ask должен использовать существующую сессию, если она передана и авторизована.
- Отсутствие `session_id` означает начало новой сессии по правилам Ask, но не означает восстановление истории.
- Неивалидный или недоступный `session_id` должен приводить к явному состоянию ошибки/пустого результата, а не к молчаливой подмене другой сессии.

### 3.2. World

```text
/world-engine?entity_id=<entity_id>&session=<session_id>
```

- `entity_id` — выбранная сущность.
- `session` — технический контекст возврата в Ask; имя параметра временно соответствует текущему frontend контракту.
- Наличие `session` не означает, что World отображает или изменяет диалог.
- При изменении контракта необходимо сохранить обратную совместимость или мигрировать все маршруты одной задачей.

### 3.3. Temporal

```text
/temporal?entity=<entity_id>&session=<session_id>&epoch=<epoch_id>
```

- `entity` — необязательный выбранный контекст сущности.
- `session` — необязательный технический контекст возврата.
- `epoch` — необязательный выбранный epoch/временной узел.
- Если связь `entity → epoch` не подтверждена `node.entity_ids`, UI может показать реальную цепочку с явным уведомлением, но не должен маркировать конкретную эпоху как связанную.

### 3.4. History

```text
/history?session_id=<session_id>
```

- `session_id` выбирает конкретную сессию для URL-восстановления.
- Отсутствие параметра означает общий список сессий/истории.
- Несуществующая сессия — явный empty/error state.
- Переход из History в Ask должен сохранять `session_id`.

## 4. Back и Refresh

### Back

Back должен восстанавливать URL-состояние последней страницы, на которой пользователь принял решение:

- Ask → World: возвращает к сессии Ask и её видимому контексту.
- World → Temporal: возвращает к выбранной сущности World.
- Temporal → World: возвращает к сущности и, если переход туда был из World, к выбранной эпохе.
- Temporal/World → Ask: возвращает к сессии Ask; origin и контекст должны быть видны пользователю.
- History → Ask: открывает выбранную сессию Ask.

Если браузерный Back невозможен из-за `window.location.href`, это не запрещает переход, но требует явной цели возврата. Предпочтительный контракт — использовать единый navigation layer с query-параметрами.

### Refresh

Refresh обязан восстановить:

1. URL-параметры;
2. backend-данные по этим параметрам;
3. текущую вкладку/режим, если он является частью deep link;
4. сообщение пользователю, если параметр недопустим или данные недоступны.

Refresh не должен:

- создавать новую сессию молча;
- менять `entity_id` на найденную «похожую» сущность;
- выбирать эпоху по первой доступной;
- показывать mock-данные вместо ошибки.

## 5. Источники истины

| Состояние | Источник истины | Что запрещено |
|---|---|---|
| `session_id` | backend auth/ReaderMemory contract | использовать ID как доказательство наличия сообщений |
| сообщения | фактический persistence endpoint Ask/ReaderMemory | восстанавливать пустой массив как будто это полная история |
| `entity_id` | World/Knowledge backend | подставлять похожую сущность |
| `entity ↔ relation` | World context relations | показывать несвязанную сущность как связанную |
| `epoch_id` | Temporal nodes | угадывать ID эпохи |
| `entity ↔ epoch` | `TemporalNode.entity_ids` / подтверждённая relation | показывать связь по одному факту наличия страницы |
| `epoch` и даты | Temporal backend bounds/uncertainty | нормализовать неопределённую дату в конкретный год |
| provenance | Knowledge/Temporal backend provenance | заменять источник LLM-резюме |
| `origin` | URL/navigation state | использовать как факт о книге |

## 6. Правила ошибок

A1R различает четыре состояния:

1. `valid`: параметр найден и backend подтвердил данные;
2. `empty`: параметр допустим, но данных для него нет;
3. `invalid`: параметр не соответствует допустимому формату или не существует;
4. `unavailable`: backend временно недоступен.

`unavailable` не превращается в `empty`, а `invalid` не заменяется другим `entity_id` или `epoch_id`.

## 7. Что не входит в A1R

- восстановление сообщений Ask после F5 — A2;
- изменение URL World при выборе сущности — A3;
- сохранение выбранного epoch и round-trip переходов — A4;
- History URL и продолжение исследования — A5;
- исправление `hybrid`, `mock` и логики доступности Temporal — A6;
- изменение API, схем, базы данных или UI.

## 8. Критерии PASS для A1R

- контракт содержит единое описание `session_id / entity_id / epoch_id / origin`;
- для каждого состояния указан источник истины;
- URL-параметры разделены по страницам;
- Back и Refresh описаны для Ask, World, Temporal и History;
- правила `empty`, `invalid`, `unavailable` разделены;
- ограничения Temporal и Knowledge не нарушены;
- ReaderMemory persistence не принят за гарантию существования сообщений;
- UI и код не изменены;
- документ не запускает A2–A6 автоматически.

## 9. Статус A1R

- **DONE:** контракт состояния определён документально.
- **DONE:** источники истины и URL-правила зафиксированы.
- **DONE:** persistence-ограничение Ask/ReaderMemory явно отмечено.
- **PROBLEMS:** реальный Ask → ReaderMemory persistence всё ещё требует проверки перед A2; это не решается в A1R.
- **Следующая задача:** A2 — восстановление Ask из ReaderMemory, но она ещё не начата.
- **OWNER-GO:** отсутствует для A2.
