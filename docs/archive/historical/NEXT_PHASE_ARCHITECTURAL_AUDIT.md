## 10. РЕКОМЕНДАЦИЯ (однозначная)

**Следующий этап: M11 — «UI очереди pending temporal-предложений» (кандидат A).**

**Почему именно он:**
1. **Законность слоя:** принцип проекта «API-first» — API готов и принят, UI — его законный потребитель. Это единственная очередь проекта, невидимая для человека-непрограммиста (вы не можете подтвердить temporal-предложения иначе как через curl).
2. **Нулевой риск ядру:** фронт не импортирует ядро, не может обойти RBAC, не может изменить WorldModel вне принятого confirm-пути. Заморозка M10 соблюдается тривиально.
3. **Нулевые новые бэкенд-контракты:** все 7 endpoint'ов уже есть; проксирование уже работает.
4. **B преждевременен по существу:** реальная потеря при рестарте — только reject-история (неудобство, не потеря данных); а честная реализация B требует изменить замороженный менеджер — прямо запрещено вашим принципом.

**Что НЕ делать сейчас:**
- persistence истории (B) — отдельное будущее решение с отдельным обоснованием изменения ядра;
- любые правки ядра M10 / TemporalEngine / provenance / ADR / канонических данных;
- расширение API M10.2 сверх принятых 7 endpoint'ов;
- фоновые сканы/автопроцессы (скан остаётся кнопкой);
- починку G3/G4/G5 (backlog, отдельные микро-задачи).

### Scope (предложение)

| Артефакт | Тип |

### DoD (предложение)

1. Страница показывает pending-предложения со всеми полями из API (id, kind, raw_text, value, line_number, context, category, confidence).
2. Кнопка «Сканировать книгу» вызывает POST scan; результат (0 новых / найдено N) виден пользователю.
3. Confirm и Reject работают через Popconfirm; после confirm — индикатор «применено, модель мира обновлена».
4. История показывает confirmed/rejected с reason.
5. Reader страницу не видит (RoleGuard editor/admin — зеркалирование бэкенд-матрицы).
6. Бэкенд не изменён ни на одну строку (git-доказательство).
