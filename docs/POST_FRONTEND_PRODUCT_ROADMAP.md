# POST_FRONTEND_PRODUCT_ROADMAP.md — дорожная карта продукта после трансформации Frontend

**Статус:** DOCUMENTED  
**Назначение:** последовательное развитие Arkaim после приёмки владельцем завершённой трансформации frontend.  
**Не является:** новым аудитом, разрешением менять все фазы сразу или заменой плану Reading.  
**Точка старта:** frontend-трансформация должна получить отдельный статус **ACCEPTED** от владельца проекта.

---

## 1. Главный принцип

Arkaim развивается как **исследовательский маршрут**, а не как набор отдельных страниц:

```text
Ask → Answer → Entity → World → Temporal → History
              ↓                         ↓
          Research Context         Time Context
              ↓                         ↓
          AI follow-up question ←────────┘
```

Главная продуктовая проблема следующей очереди — сделать уже существующие данные связанными, объяснимыми и возвращаемыми. Новые визуальные элементы нельзя добавлять раньше реальной связи в данных и API.

### Обязательные архитектурные ограничения

1. Книга и существующие слои Pulse остаются первичным источником истины.
2. LLM формулирует голос, но не является источником фактов и не создаёт отсутствующие связи.
3. Если backend не подтверждает `entity ↔ event/time`, интерфейс не должен визуально изображать такую связь как доказанную.
4. Любое значение из KnowledgeLayer должно быть связано с источником и эпистемическим статусом, если эти данные уже представлены в модели.
5. ReaderMemory хранит историю читателя, но не подменяет знания о книге.
6. ReaderWW и World Engine не выполняют автономные публикации, рассылки или другие внешние действия.
7. Каждая фаза сначала превращается в отдельный план, затем — в одну ограниченную инженерную задачу.

## 2. Обязательный рабочий цикл

```text
Выбрать одну фазу
  ↓
Проверить её план и границы
  ↓
Выбрать одну конкретную задачу
  ↓
Реализовать и проверить
  ↓
Обновить документацию и журнал статусов
  ↓
Получить OWNER-GO
  ↓
Перейти к следующей задаче
```

### Что означает `OWNER-GO`

`OWNER-GO` — явное решение владельца проекта начать **следующую** задачу или фазу. Он не выдаётся автоматически после тестов и не означает разрешение выполнять весь roadmap одним заданием.

### Запрещено

- выполнять фазы A–G одним большим заданием;
- переходить к следующей фазе без `OWNER-GO`;
- объявлять функцию готовой только потому, что появился визуальный экран;
- подменять реальные данные mock-контентом;
- считать неподтверждённую связь фактом;
- менять требования к Reading внутри другой фазы без отдельного решения;
- одновременно расширять продукт и выполнять массовый технический долг, если владелец не утвердил такое изменение приоритета.

# Фаза A — Core Flow

## Цель

Довести базовый пользовательский маршрут от вопроса до истории так, чтобы пользователь не терял контекст, мог вернуться назад и после перезагрузки продолжить с того же места.

```text
Ask → Answer → Entity → World → Temporal → History
```

## Что улучшить

1. **Ответ и контекст**
   - отделить текст ответа от служебного и исследовательского контекста;
   - явно показывать, какие сущности и источники относятся к ответу;
   - сохранить стриминг, Markdown и авторский UX `arkaim-web`.

2. **EntityCard**
   - показывать имя, тип, краткое описание и доступные действия;
   - вести в World с идентификатором сущности;
   - показывать переход в Temporal только при наличии подтверждённого временного контекста;
   - при отсутствии связи объяснять это, а не создавать ложную ссылку.

3. **Навигация**
   - сохранять `entity_id`, `session_id` и иные реальные параметры при переходах;
   - обеспечить возврат World → Ask и Temporal → World;
   - определить поведение Back Browser: возврат к выбранной сущности и сессии, а не в общий список.

4. **История**
   - показывать вопрос, ответ и связанные сущности из реальной ReaderMemory;
   - открывать конкретную сессию;
   - сохранять позицию и выбранный контекст после F5;
   - не подменять ошибки чтения истории mock-диалогом.

5. **Персистентность**
   - проверить восстановление сессии авторизации, диалога и выбранной сущности;
   - отдельно проверить недоступность API и корректное восстановление после повторного запроса.

## Последовательность задач фазы A

1. **A1 — Карта состояния маршрута**
   - исследовать фактическое состояние Ask → Answer → Entity → World → Temporal → History;
   - зафиксировать источники истины, переходы и точки потери состояния;
   - результат: исследовательский отчёт без изменения кода.

2. **A1R — Контракт состояния маршрута**
   - определить единый контракт `session_id / entity_id / epoch / origin`;
   - определить правила URL, Back и Refresh и источник истины каждого состояния;
   - **без реализации UI**.

3. **A2 — Восстановление Ask из ReaderMemory**
   - после F5 восстановить сообщения текущей сессии;
   - открыть `/ask?session_id=...`;
   - проверить Refresh и Back.

4. **A3 — Синхронизация World с URL**
   - отражать выбранную сущность в URL;
   - открывать deep link именно выбранной сущности;
   - проверить Back/Forward.

5. **A4 — Сохранение контекста Temporal**
   - сохранять `session_id + entity + epoch`;
   - проверить переходы Temporal ↔ Ask/World без потери контекста.

6. **A5 — History deep links**
   - отражать выбранную сессию в URL;
   - позволить продолжить исследование из History без потери контекста.

7. **A6 — Корректность состояний и ошибок**
   - убрать ложный `hybrid`;
   - убрать misleading `mock` для реальной ошибки;
   - показывать Temporal только при подтверждённой связи.

> Каждая следующая задача начинается только после отдельного `OWNER-GO`. Нельзя объединять A1R–A6 в один пакет.

## Критерии приёмки фазы A

- пользователь проходит весь маршрут без ручного копирования идентификаторов;
- Back и F5 сохраняют выбранную сущность, сессию и разумную позицию;
- EntityCard не показывает неподтверждённый Temporal-переход;
- ответ и история связаны одной сессией;
- загрузка, пустое состояние, API-ошибка и отсутствие связи обработаны явно;
- unit-, integration- и browser-проверка проходят;
- нет mock-данных на критическом маршруте.

**Фаза считается VERIFIED только после проверки. Следующая фаза требует OWNER-GO.**

# Фаза B — World Engine

## Цель

Сделать World самостоятельным исследовательским пространством, где пользователь может не только открыть сущность, но и понять её связи, окружение, события, источники и временной контекст.

## Что развивать

1. полноценная карточка и страница сущности;
2. связи `entity → related entity`;
3. типы связей и объяснение их направления;
4. события и места, связанные с сущностью;
5. временной контекст сущности;
6. источники и provenance;
7. навигация по графу без потери выбранной ветки;
8. deep links, восстановление состояния и возврат к исходному ответу.

## Принципы данных

- каждая связь должна иметь подтверждённый backend-источник;
- если причина связи неизвестна, нельзя придумывать категорию;
- отсутствие связи является допустимым результатом, а не ошибкой данных;
- один и тот же термин должен разрешаться в одну каноническую сущность с возможностью показать неоднозначность;
- графическое расстояние не должно выдаваться за доказательство смысловой близости.

## Предлагаемое разбиение на задачи

1. **B1 — Модель карточки сущности**
   - описать поля, типы связей, источники, временные данные и неизвестные значения.

2. **B2 — Исследование одной сущности**
   - собрать единый маршрут: описание → связи → события → время → источники → Ask.

3. **B3 — Переходы между сущностями**
   - реализовать `entity → related entity` с сохранением origin и Back-контекста.

4. **B4 — Навигация внутри World**
   - фильтры, группировка, пустые состояния, глубокие ссылки и восстановление после обновления.

## Критерии приёмки фазы B

- одна сущность доступна по прямой ссылке;
- все показанные связи подтверждены данными;
- можно перейти к связанной сущности и вернуться к исходной;
- события, место и время показаны только при наличии связи;
- источник каждого ключевого утверждения доступен из карточки;
- отсутствие данных не маскируется mock-контентом;
- World не становится отдельным продуктом с собственной «историей правд»: источником остаётся Pulse/Knowledge.

**Переход к Temporal — только после OWNER-GO.**

# Фаза C — Temporal

## Цель

Превратить Temporal в рабочий инструмент для понимания событий, периодов и эпох мира, связанных с сущностями и утверждениями.

## Что развивать

1. полноценная вертикальная и/или горизонтальная шкала;
2. события, периоды и эпохи с различимыми типами;
3. связи `entity ↔ event ↔ time`;
4. раскрытие контекста события;
5. переход из события к сущностям и обратно;
6. provenance каждого временного утверждения;
7. обработка неопределённого, спорного или неизвестного времени;
8. deep links и возврат к предыдущему контексту.

## Важное правило

Если дата не подтверждена, интерфейс должен обозначать это как **неопределённое время**, а не угадывать год. Если источники расходятся, нужно показать варианты и их статус, а не выбирать удобную дату.

## Предлагаемое разбиение на задачи

1. **C1 — Контракт временной шкалы**
   - типы узлов, диапазоны, неопределённость, сортировка, deep-link параметры.

2. **C2 — Шкала и фильтры**
   - читаемая шкала, периоды, эпохи, события, переходы и loading/empty/error states.

3. **C3 — Контекст события**
   - описание, участвующие сущности, места, связанные утверждения и источники.

4. **C4 — Round-trip навигация**
   - Temporal → Entity → Ask и возврат к выбранному событию без потери состояния.

## Критерии приёмки фазы C

- событие можно открыть и понять без чтения кода или URL;
- каждая показанная связь с сущностью подтверждена;
- неизвестное время не превращается в выдуманную дату;
- конфликтующие даты видны и не сглаживаются;
- у каждого временного утверждения доступен provenance;
- переходы туда и обратно сохраняют контекст;
- шкала остаётся читаемой на разных размерах окна.

**Переход к Knowledge & Provenance — только после OWNER-GO.**

# Фаза D — Knowledge & Provenance

## Цель

Дать пользователю возможность понимать не только **что** Arkaim сообщает, но и **почему**, с какой степенью уверенности и на основании каких сведений.

## Что развивать

1. Knowledge Cards;
2. источники и ссылки на конкретные места доказательства;
3. степень уверенности и эпистемический статус;
4. подтверждённые, предполагаемые, спорные и неизвестные сведения;
5. конфликтующие утверждения;
6. исправление информации во времени без переписывания истории доказательств;
7. переход `утверждение → источник`;
8. cross-source reasoning с видимой цепочкой оснований;
9. связь Knowledge Card с Entity, Event и World.

## Правила представления

- уверенность не должна изображаться как вероятность, если модель не задаёт такой смысл;
- источник должен указывать, какое утверждение поддерживает, а не только на файл;
- исправленная версия и прежняя версия сохраняются как разные состояния знания;
- LLM-резюме не должно выглядеть как первоисточник;
- cross-source reasoning должен показывать используемые основания и ограничения вывода.

## Предлагаемое разбиение на задачи

1. **D1 — Таксономия Knowledge Cards**
   - тип, утверждение, статус, уверенность, источники, дата состояния, противоречия.

2. **D2 — Карточка и раскрытие источников**
   - переход от утверждения к доказательству и обратно.

3. **D3 — Конфликты и исправления**
   - отображение версий, статуса и авторства изменения без автономной публикации.

4. **D4 — Cross-source reasoning**
   - показать основания вывода, промежуточные утверждения и уровень поддержки.

## Критерии приёмки фазы D

- каждое проверяемое утверждение можно открыть до его источника;
- статус уверенности объяснён пользователю обычным языком;
- конфликт не скрывается и не разрешается произвольно;
- исправления видны во времени;
- рассуждение воспроизводимо по предоставленным основаниям;
- Knowledge не подменяется LLM-фантазией;
- сведения без источника явно отображаются как неподтверждённые, а не как истина.

**Переход к AI Research — только после OWNER-GO.**

# Фаза E — AI Research

## Цель

Сделать диалог продолжением исследования, а не серией независимых вопросов.

```text
спросил → ответил → выбрал сущность → исследовал → перешёл во время
→ задал следующий вопрос с сохранённым контекстом
```

## Что развивать

1. контекст предыдущих вопросов;
2. выбранная сущность как явный контекст;
3. вопрос к конкретной сущности;
4. вопрос к событию, периоду или эпохе;
5. уточняющие вопросы;
6. переход от неоднозначного вопроса к выбору трактовки;
7. более глубокие цепочки исследования;
8. отображение того, какой контекст был передан системе;
9. возможность сбросить или изменить контекст.

## Обязательные ограничения

- контекст Research не должен молча менять первичный источник истины;
- выбранная сущность должна быть видима пользователю как активный контекст;
- система не должна утверждать, что помнит больше, чем реально сохранено;
- источник ответа сохраняется по тому же Voice-протоколу: Pulse ищет ответ, Voice формулирует, Pulse проверяет;
- уточняющий вопрос предпочтительнее многословного предположения.

## Предлагаемое разбиение на задачи

1. **E1 — Research Context**
   - формализовать session, entity, event/time selection и явное удаление контекста.

2. **E2 — Контекстный Ask**
   - передавать выбранный контекст в backend и отображать его в Ask.

3. **E3 — Уточняющие вопросы**
   - поддержать безопасное уточнение при неоднозначности.

4. **E4 — Глубина исследования**
   - собрать цепочки Ask → Entity → Event → Ask с проверяемыми основаниями.

## Критерии приёмки фазы E

- активный контекст всегда виден;
- новый вопрос действительно использует выбранный контекст;
- пользователь может сбросить контекст и задать независимый вопрос;
- история вопросов соответствует фактически отправленному контексту;
- уточняющий вопрос не блокирует исследование без причины;
- LLM-сообщения не становятся источником Knowledge;
- сквозной сценарий проходит с ReaderMemory и возвратом в World/Temporal.

**Переход к Reading — только после OWNER-GO.**

# Фаза F — Reading

## Цель

Развить Reading как отдельный большой продуктовый поток после стабилизации Core Flow, World, Temporal и Knowledge.

> В текущем дереве репозитория отдельный файл `READING_UX_REDESIGN_PLAN.md` не найден. Поэтому содержание фазы F ниже является границей roadmap, но **не заменой отсутствующему подробному плану Reading**. Перед началом фазы такой план должен быть найден, восстановлен из согласованного источника или создан и отдельно принят владельцем.

## Что развивать

1. полноценное чтение;
2. прогресс чтения;
3. главы и секции;
4. контекст мира рядом с текстом;
5. связанные сущности и события;
6. переходы между текстом и World/Temporal;
7. сохранение позиции;
8. корректная работа при перезагрузке и смене устройства, если синхронизация предусмотрена backend;
9. доступность и комфортное чтение на мобильном экране.

## Предлагаемое разбиение на задачи

1. **F0 — Подтвердить отдельный план Reading**
   - определить документ-источник истины, версию, владельца и критерии приёмки.

2. **F1 — Минимальный Reading flow**
   - открыть книгу → выбрать раздел → читать → вернуться на позицию.

3. **F2 — Контекст чтения**
   - показывать World/Temporal-связи только из подтверждённых данных.

4. **F3 — Прогресс и восстановление**
   - сохранять позицию и обрабатывать конфликт версий без потери чтения.

## Критерии приёмки фазы F

- существует утверждённый `READING_UX_REDESIGN_PLAN.md` или его эквивалент;
- текст читается без технических блокировок и потери прогресса;
- позиция сохраняется после обновления страницы;
- переход к сущности и событию сохраняет источник перехода;
- связанные данные не выдумываются;
- Reading не реализуется за счёт разрушения уже проверенного Ask/World/Temporal маршрута.

**Переход к Product Hardening — только после OWNER-GO.**

# Фаза G — Product Hardening

## Цель

После функционального развития довести продукт до устойчивого состояния для реального использования.

## Направления

1. UX и доступность;
2. все loading states;
3. понятные ошибки и повторные действия;
4. пустые состояния без mock-данных;
5. мобильная версия;
6. PWA и оффлайн-поведение;
7. производительность;
8. ESLint/TypeScript;
9. backend performance и timeouts;
10. наблюдаемость критического маршрута;
11. безопасность и корректное обращение с пользовательскими данными;
12. актуальная документация и удаление временного v2-референса только по отдельному решению.

## Предлагаемое разбиение на задачи

1. **G1 — Reliability audit выбранного маршрута**
   - loading, error, retry, empty, offline, refresh.

2. **G2 — Производительность**
   - измерить критические страницы и API, устранить повторные тяжёлые запросы и ненужный ре-рендер.

3. **G3 — Mobile и PWA**
   - проверить Reading, Ask и World на узком экране; обновить service worker после проверки cache strategy.

4. **G4 — Технический долг**
   - устранять только долг, затрагивающий выбранный пользовательский поток или блокирующий релиз.

5. **G5 — Release gate**
   - полный тестовый прогон, ручной маршрут, known issues и решение владельца о выпуске.

## Критерии приёмки фазы G

- критический маршрут не показывает бесконечную загрузку или неясную ошибку;
- reload, offline и retry проверены;
- мобильный маршрут не блокирует основные действия;
- PWA не показывает устаревший API-кэш после деплоя;
- критические performance-метрики зафиксированы до и после изменения;
- TypeScript и ESLint не скрывают новые критические ошибки;
- полный browser-прогон проходит;
- выпуск одобрен владельцем отдельно.

## 4. Сквозные требования качества

Эти требования применяются ко всем фазам, а не только к Product Hardening.

### 4.1. Источники истины

- frontend не создаёт факты и отношения;
- backend-контракт отделяет факт от гипотезы, неизвестного и ошибки загрузки;
- mock-данные допустимы только в изолированных тестах или демонстрационных режимах с явной маркировкой;
- production UI не заменяет API-ошибку фиктивным содержимым.

### 4.2. Персистентность

Для каждого нового контекста должно быть определено:

| Контекст | Где хранится во время навигации | Где восстанавливается после reload | Владелец данных |
|---|---|---|---|
| session | URL/состояние Ask | session_id/localStorage/cookie по текущему контракту | Backend ReaderMemory |
| entity | URL query + локальное состояние | тот же deep link | World/Knowledge backend |
| event/time | URL query + локальное состояние | тот же deep link | Temporal backend |
| Knowledge selection | URL/состояние карточки | восстановление по идентификатору | KnowledgeLayer |
| Reading position | отдельный reader state | серверная позиция при наличии поддержки | Reader/Backend |

Если конкретный механизм ещё не определён, это задача плана, а не повод сохранять только в нестабильном React-state.

### 4.3. Ошибки

Каждый пользовательский поток должен различать:

- данных пока нет;
- backend подтвердил отсутствие связи;
- запрос завершился ошибкой;
- пользователь не авторизован;
- срок доступа истёк;
- соединение отсутствует;
- данные устарели и могут быть перезагружены.

### 4.4. Доступность

- клавиатурная навигация;
- видимый focus;
- корректные labels;
- не только цветовой код для статуса и типов связей;
- достаточный contrast;
- поддержка reduced motion;
- semantic timeline/navigation.

### 4.5. Тестирование

Для каждой задачи выбирается минимально достаточный набор:

1. unit-тесты бизнес-логики и контрактов;
2. integration/API-тесты для persistence и связей;
3. component-тесты для пустых, ошибочных и подтверждённых состояний;
4. Playwright — только для важных сквозных маршрутов;
5. ручная браузерная проверка обязательна для UX-решения;
6. проверка reload и Back для любого нового deep-link контекста.

## 6. Итоговый маршрут продукта

После прохождения фаз ожидаемый пользовательский сценарий выглядит так:

```text
1. Читатель задаёт вопрос.
2. Arkaim отвечает и показывает подтверждённые сущности/источники.
3. Читатель открывает сущность в World.
4. Исследует связи, события, места и время.
5. Видит, какие утверждения подтверждены, спорны или неизвестны.
6. Возвращается в Ask с явным сохранённым контекстом.
7. Задаёт следующий вопрос.
8. Открывает историю и продолжает предыдущую сессию.
9. При необходимости переходит в Reading и возвращается в World с позиции текста.
10. После перезагрузки продолжает с тем же сохранённым контекстом.
```

Именно этот маршрут, а не количество страниц или отдельных компонентов, является критерием зрелости следующей версии Arkaim.

## 7. Ближайшее допустимое действие

Эта дорожная карта сама по себе **не запускает разработку**.

Ближайший допустимый процесс:

1. владелец подтверждает завершение frontend-трансформации как **ACCEPTED**;
2. владелец выбирает фазу A;
3. для фазы A составляется отдельный план;
4. выбирается только первая задача;
5. задача выполняется и проверяется;
6. после отчёта владелец выдаёт или не выдаёт `OWNER-GO`.

Следующая фаза не начинается автоматически после прохождения тестов.
