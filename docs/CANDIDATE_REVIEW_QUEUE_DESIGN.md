# Очередь проверки кандидатов LLM — проектное решение

- **Дата:** 2026-10-28
- **Статус:** **Q1 (индекс) + Q2 (решения) — IMPLEMENTED + TESTED**, Q3 (API) и
  Q4 (экран) — запланированы. Решения владельца зафиксированы (раздел 12).
- **Связанные этапы:** 6c (маркировка кандидатов), 6d (гейт в RAG/карточках),
  6e (гейт в WORLD MODEL)
- **Основание:** живой прогон GigaChat 2026-10-28 дал первого реального
  кандидата, который прошёл через все гейты (см. раздел 2). Дальше нужно
  место, где автор этого кандидата увидит и примет решение.

---

## Простыми словами

1. **Зачем это нужно.** Сейчас LLM может предложить знание, и оно безопасно
   лежит в файле с пометкой «не проверено». Но у автора нет удобного способа
   это увидеть и сказать «да» или «нет».
2. **Что предлагается.** Небольшая очередь проверки: список предложений,
   у каждого две кнопки — «Принять» и «Отклонить», с обязательным
   комментарием. Решение записывается прямо в саму запись знания, поэтому
   все уже существующие защиты (RAG, карточки, WORLD MODEL) начинают
   работать без единой правки.
3. **Главный принцип.** Одобрение означает «автор согласен, что это честная
   системная интерпретация», а **не** «это стало каноном книги». Канон
   по-прежнему только у автора и только вручную.
4. **Что важно для безопасности.** LLM и фоновые процессы физически не могут
   поставить «одобрено». Это делает только человек с правами автора, и каждое
   решение навсегда попадает в журнал.
5. **Сколько работы.** Ориентировочно 2–3 дня: серверная часть ~1,5 дня,
   экран ~1 день, тесты входят в эти оценки.

## 1. Задача и границы

**Цель:** дать автору рабочий цикл

```
LLM candidate → review → approved / rejected → (RAG, карточки, WORLD MODEL)
```

**Входит в задачу:**

- список кандидатов с фильтрами;
- решение «принять / отклонить / вернуть в проверку»;
- запись решения в запись знания + неизменяемый журнал;
- права: решение принимает только автор/администратор;
- тесты, доказывающие, что без решения кандидат никуда не попадает, а после
  «принять» — попадает штатным путём.

**Не входит:**

- редактирование текста кандидата (правка = отклонить и перегенерировать;
  ручное редактирование — отдельная задача);
- автоматическое одобрение (по таймеру, по уверенности, по количеству
  источников — запрещено архитектурным принципом «никаких автономных
  действий»);
- перенос кандидатов в канон (`AUTHOR_CANON`) — это отдельное решение автора
  и отдельный инструмент;
- мобильное приложение;
- живой вызов LLM из очереди.

запуски (CLI/админ-действие), не планировщик.

## 3. Ключевое проектное решение: где живёт статус

**Решение: статус живёт только в самой записи знания (`_provenance_metadata`).**

Почему не отдельная база/таблица очереди:

- появился бы второй источник истины: запись говорит одно, очередь другое;
- гейты 6d/6e читают файлы — пришлось бы синхронизировать их с базой;
- потеря/рассинхрон базы означал бы утечку кандидата в мир.

Очередь — это **представление** (индекс, собираемый сканированием файлов),
а не хранилище. Журнал решений — отдельный append-only файл (аудит), но он
не влияет на гейты: истина всегда в записи.

## 4. Модель данных

### 4.1. Запись знания (существующие поля + новые)

```jsonc
{
  "topic": "Сварга",
  "content": "...",
  "layers": { "literal": "...", "metaphorical": "...", "cosmic": "..." },
  "_provenance_metadata": {
    "category": "DERIVED",
    "provenance_category": "SYSTEM_INTERPRETATION",
    "source_level": "SYSTEM_INTERPRETATION",
    "source": "LLM",
    "requires_author_review": true,
    "status": "APPROVED",              // PENDING_REVIEW | APPROVED | REJECTED
    "model": "GigaChat",               // кто сгенерировал (для аудита)
    "generated_at": "2026-10-28T12:29:53Z",
    "reviewed_by": "author",           // кто решил
    "reviewed_at": "2026-10-29T09:10:00Z",
    "review_comment": "Формулировка согласуется с главой 4",
    "previous_status": "PENDING_REVIEW"
  }
}
```

Новые поля — только `reviewed_by`, `reviewed_at`, `review_comment`,
`previous_status`, `model`, `generated_at`. Существующие предикаты от них не
зависят, поэтому старые файлы читаются как раньше.

### 4.2. Идентификатор кандидата

Стабильный, вычисляемый, не зависящий от порядка записей:

```
candidate_id = "cand_" + sha1(
    имя_файла + "|" + topic + "|" + content + "|" + layers.literal
)[:12]
```

`layers.literal` входит в хеш, потому что у записей пайплайна `content`
часто пуст, а смысл лежит в слоях.

- перестановка записей в файле id не меняет;
- правка текста даёт новый id (это честно: изменился кандидат); история
  прежнего остаётся в журнале;
- коллизия возможна только при полном совпадении файла, темы и текста —
  такие записи и так дубликаты (отдельный известный дефект данных).

Индекс также хранит `locator` (`ФАЙЛ.json#items[7]`) для точечной записи.

### 4.3. Журнал решений (аудит)

`core/OS_DATA/review/decisions.jsonl`, одна строка = одно решение:

```json
{"ts":"2026-10-29T09:10:00Z","actor":"author","action":"approve",
 "candidate_id":"cand_1a2b3c4d5e6f","file":"THEMES_EXPANDED.json",
 "locator":"THEMES_EXPANDED.json#items[3]","topic":"Сварга",
 "from":"PENDING_REVIEW","to":"APPROVED","comment":"...","request_id":"..."}
```

Журнал только дописывается; правка/удаление строк запрещены кодом.
Он не участвует в гейтах — это след для разбора, а не источник истины.

## 5. Жизненный цикл и правила переходов

| Из | В | Кто может | Условие |
|---|---|---|---|
| (нет) | `PENDING_REVIEW` | только пайплайн LLM (явный запуск) | всегда ставит флаг проверки |
| `PENDING_REVIEW` | `APPROVED` | автор/админ | комментарий обязателен |
| `PENDING_REVIEW` | `REJECTED` | автор/админ | причина обязательна |
| `REJECTED` | `PENDING_REVIEW` | автор/админ | «вернуть в проверку», причина обязательна |
| `APPROVED` | `REJECTED` | автор/админ | отзыв одобрения; причина обязательна |
| `APPROVED` | `PENDING_REVIEW` | **запрещено** | сначала отзыв (двухшагово) |
| любой | `APPROVED` | LLM/планировщик/скрипт | **запрещено на уровне API** |

Правила:

1. **LLM никогда не ставит `APPROVED`** — только `PENDING_REVIEW`.
2. **Нет автоодобрения** по времени, уверенности, количеству источников.
3. **`APPROVED` ≠ канон.** `provenance_category` остаётся
   `SYSTEM_INTERPRETATION`; в `AUTHOR_CANON` запись не переводится.
4. **Отклонение необратимо только по смыслу:** текст остаётся в файле
   (гейт его блокирует), вернуть в проверку можно явным действием.
5. **Массовое одобрение** — только по явному выбору автора, с записью
   решения по каждой записи отдельно (никаких «одобрить весь файл» одной
   кнопкой).

## 6. API (черновик контракта)

Все эндпоинты требуют аутентификации; решения — роль `author`/`admin`.
Остальные роли видят список, но получают 403 на решение.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/candidates` | список: фильтры `status`, `file`, `source`, `q`, `limit`, `offset`; сортировка по дате генерации |
| `GET` | `/api/candidates/stats` | счётчики по статусам/файлам (для бейджа) |
| `GET` | `/api/candidates/{candidate_id}` | карточка: текст, слои, провенанс, ссылка на источник (`derived_from`), история из журнала |
| `POST` | `/api/candidates/{candidate_id}/approve` | `{comment, expected_status}` |
| `POST` | `/api/candidates/{candidate_id}/reject` | `{comment, expected_status}` |
| `POST` | `/api/candidates/{candidate_id}/reopen` | `{comment}` |

Ответы:

- `200` — обновлённая запись и `candidate_id`;
- `400` — пустой комментарий там, где он обязателен;
- `403` — нет роли;
- `404` — id не найден (файл пересобран/удалён);
- `409` — `expected_status` не совпал (запись уже изменили) — защита от
  «двойного клика» и параллельных вкладок;
- `422` — невалидное тело.

`expected_status` передаётся клиентом из карточки: если состояние успело
измениться, сервер не перезаписывает решение молча.

## 7. Запись и конкурентность

1. Читаем файл, находим запись по `locator` и сверяем `candidate_id`
   (защита от сдвига индексов).
2. Меняем только поля ревью; остальные поля и порядок записей не трогаем.
3. Пишем атомарно: временный файл в том же каталоге → `os.replace`.
4. Перед заменой — бэкап в `core/OS_DATA/review/backups/<timestamp>-ФАЙЛ.json`
   (каталог вне `core/KNOWLEDGE`, чтобы не засорять знания).
5. Формат сохраняем: если файл был массивом — остаётся массивом; если
   `{"items": [...]}` — остаётся объектом с теми же служебными полями;
   BOM и завершающий перевод строки сохраняются как были.
6. Блокировка на файл (lock-файл рядом) — на время чтения-записи; очередь
   индексируется заново после каждого решения.
7. Журнал дописывается после успешной записи; если журнал недоступен, файл
   знания откатывается к бэкапу — решения без аудита не бывает.

Индекс: сканирование 53 файлов занимает единицы миллисекунд, поэтому кеш не
нужен; при желании — кеш по `mtime`.

## 8. Экран (минимальный)

- Список: тема, файл-источник, дата, статус, короткий фрагмент.
- Фильтры: «ждут проверки» (по умолчанию), «одобренные», «отклонённые»,
  поиск по теме.
- Карточка: три уровня смысла, связи, ссылка «откуда» (`derived_from`),
  пометка «системная интерпретация, не канон».
- Кнопки: «Принять» (комментарий), «Отклонить» (причина), «Вернуть в
  проверку».
- Счётчик в навигации: сколько ждёт решения.
- Тексты кандидата на экране не редактируются.

---

## 9. Тесты (обязательный минимум)

1. Кандидат появляется в списке после генерации.
2. Без решения не виден ни в RAG, ни в карточках, ни в WORLD MODEL
   (гейты 6d/6e — уже есть, здесь проверяется сквозной сценарий).
3. `approve` меняет статус и запись начинает проходить гейты (RAG/карточки/
   мир) — «проверенный источник продолжает проходить как раньше».
4. `reject` блокирует запись, текст остаётся в файле.
5. `reopen` возвращает в `PENDING_REVIEW`.
6. Пустой комментарий → 400; нет роли → 403; неизвестный id → 404;
   устаревший `expected_status` → 409.
7. Повторный `approve` идемпотентен (не создаёт вторую строку журнала с
   другим результатом).
8. LLM/планировщик не может вызвать решение (проверка на уровне API и на
   уровне сервиса).
9. `APPROVED` не меняет `provenance_category` на канон.
10. Атомарность: сбой записи не оставляет частично обновлённый файл.
11. Журнал: ровно одна строка на решение, поля обязательные.
12. Форматы: работа с bare-list и wrapped-файлами; чужие поля не теряются.

## 11. Риски и как они снимаются

| Риск | Снятие |
|---|---|
| Массовое «одобрить всё» без чтения | решение по каждой записи, комментарий обязателен |
| Случайное одобрение из-за гонки вкладок | `expected_status` → 409 |
| Порча файла знаний при записи | атомарная замена + бэкап + тесты форматов |
| Подмена смысла: «одобрено» = «канон» | отдельное поле не меняется; в UI явная пометка |
| LLM или фон сам одобряет | запрет в сервисе + тест 8 |
| Очередь расходится с файлами | индекс всегда строится из файлов; журнал не влияет на гейты |

## 12. Решения владельца (2026-10-28)

1. **Роли:** решения принимают только `author` и `admin`.
2. **Комментарий:** при `APPROVED` обязателен; достаточно одной строки с
   обоснованием. (Принято для всех решений — так проще аудит.)
3. **`REJECTED`:** остаётся в исходном файле с явным статусом и provenance;
   отдельного карантина в первой версии нет.
4. **Перегенерация и массовое одобрение:** отложены до v2; в первой версии —
   только ручная работа с отдельным кандидатом.

Уточнения по реализации:

- **Бэкапы** кладутся в `core/OS_DATA/review/backups/` (каталог в `.gitignore`),

- **Приёмочный прогон на копии реальных данных:** живой ответ GigaChat добавлен
  в настоящий `THEMES_EXPANDED.json` (14 записей); до решения слой знаний —
  13 тем и 1 пропущенный кандидат; после `approve` — 14 тем, кандидат проходит
  гейт мира, журнал 1 строка, исходные файлы репозитория не изменены.

## 14. Итог

Проект опирается на уже работающие гейты и не создаёт второго источника
истины. Реализация не меняет ни канон, ни правила провенанса: она только
даёт автору способ поставить `APPROVED`, который гейты уже умеют читать.
