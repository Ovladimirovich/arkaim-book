# Архитектурная записка: три хранилища одобрений

**Дата:** 2026-10-29
**Статус:** зафиксировано, требует решения владельца
**Связано с:** закрытым техническим пробелом `POST /book/research-engine/apply/{job_id}`

---

## Простыми словами

Система «Наследие Аркаима» хранит одобрённые знания в трёх разных местах,
и они не знают о друг о друге. Когда владелец одобряет факт через одно
окно, это одобрение не появляется в двух других. Это не баг текущего
кода, а архитектурное решение, принятое при разработке M7, M10 и Q1–Q4
отдельно. До решения владельца синхронизация не выполняется.

---

## Хранилища

### 1. Канонический World Model
- **Файл:** `core/CORE/narrative_engine/data/WORLD_MODEL.json`
- **Что хранит:** эпохи, локации, цивилизации, технологии, канонические
  события — структурная модель мира.
- **Как пишется:** только через `TemporalUpdateManager.confirm()`
  (M10 confirm route, `POST /book/temporal/pending-updates/{id}/confirm`).
  Инвариант: «strictly suggest-only, без confirm() WorldModel НЕ изменяется».
- **Статус записи:** `confirmed` / `rejected` (в in-memory менеджере).
- **Кто вызывает:** editor/admin через M10 route.

### 2. Очередь проверки кандидатов (Q1–Q4)
- **Файл решений:** `core/OS_DATA/review/decisions.jsonl`
- **Файл кандидатов:** `core/KNOWLEDGE/*.json` (конкретный файл зависит
  от темы, например `ARCHAEOLOGY.json`, `CROSS_REFERENCES.json`).
- **Что хранит:** решения о кандидатах LLM — `approved` / `rejected`
  с указанием автора и комментария.
- **Как пишется:** через review queue API
  (`POST /book/knowledge/review/{candidate_id}/approve` и `/reject`).
- **Кто вызывает:** author/admin (Q4 RBAC).
- **Влияние на World Model:** одобренный кандидат становится
  «проверенным» (verified) для World Model — но сам факт, что он одобрен,
  не пишется в `WORLD_MODEL.json`. World Model узнаёт об одобрении
  через кросс-линковку (screenplay_scene_world_links), а не через
  direct sync.

### 3. Коррекции (M7)
- **Файл:** `core/OS_DATA/corrections.json`
- **Что хранит:** явные коррекции фактов, предложенные пользователем
  или системой.
- **Как пишется:** через `POST /book/corrections` (editor/admin).
- **Кто вызывает:** editor/admin.
- **Влияние на World Model:** коррекция не автоматически
  применяется к `WORLD_MODEL.json` — она создаётся как отдельная запись,
  и её применение к модели мира требует отдельного действия
  (M10 confirm или ручное вмешательство).

## Где возникает расхождение

| Сценарий | Что происходит | Где фиксируется | Где НЕ фиксируется |
|---|---|---|---|
| Владелец одобряет кандидата LLM через Q4 | Кандидат помечается `approved` в `decisions.jsonl` | Q-хранилище | `WORLD_MODEL.json` не получает тег «одобрено владельцем» |
| Владелец подтверждает temporal-находку через M10 | Эпоха/событие в `WORLD_MODEL.json` обновляется | M10-хранилище (в самом файле) | Q-хранилище не знает о подтверждении |
| Пользователь отправляет коррекцию через M7 | Коррекция сохраняется в `corrections.json` | M7-хранилище | `WORLD_MODEL.json` не обновляется автоматически |
| Кандидат одобрен (Q4), но не подтверждён temporal-находкой (M10) | Кандидат «проверен», но World Model не знает об этом | Q-хранилище | World Model может показывать устаревшую информацию |

---

## Варианты решения

### Вариант A: One-way sync (Q → World Model)
После одобрения кандидата через Q4 автоматически создаётся
temporal-находка в M10, которую владелец подтверждает в один клик.
- **Плюс:** минимальное изменение, не нарушает инвариант M10.
- **Минус:** две операции вместо одной; owner может забыть подтвердить.

### Вариант B: Shared approval registry
Единый реестр одобрений (`core/OS_DATA/approval_registry.jsonl`),
в который пишут все три системы. World Model читает реестр при загрузке.
- **Плюс:** единый источник истины, прозрачность.
- **Минус:** новая подсистема; требует миграции существующих данных;
  нарушает принцип «не создавать параллельную систему, если можно
  расширить существующую».

### Вариант C: Lazy reconciliation
При загрузке World Model сканирует `decisions.jsonl` и
`corrections.json`, строит эффективный набор одобренных записей.
- **Плюс:** не требует изменения существующих потоков.
- **Минус:** медленнее; сложнее отлаживать; риск рассинхронизации
  при частичных сбоях.

### Вариант D: Оставить как есть
Три хранилища работают независимо. World Model — первичный
структурный источник; Q-хранилище — источник доверия к кандидатам;
M7 — источник пользовательских коррекций. Синхронизация не требуется,
потому что каждая система решает свою задачу.
- **Плюс:** минимум изменений, минимум рисков.
- **Минус:** owner видит разрозненную картину; не понятно,
  какой факт актуален без проверки всех трёх мест.

## Рекомендация инженера

До принятия решения владельцем рекомендуется **Вариант D**
(оставить как есть), потому что:
1. Каждая система уже работает и покрыта тестами.
2. Ни один из вариантов не является срочным — текущая расхождение
   не приводит к корректности данных, только к UX-запутённости.
3. Выбор варианта требует понимания, какой тип знаний будет
   доминировать в будущем (кандидаты LLM, temporal-находки,
   пользовательские коррекции).

Решение владельца фиксируется здесь. До решения — никаких миграций.
