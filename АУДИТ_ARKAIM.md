## 1. Объект аудита

### 1.1. Что анализируется

Проект «Наследие Аркаима» — программная система, которая представляет книгу как цифровое сознание. Главная идея: ядро книги знает факты само, а большие языковые модели используются только для формулировки ответа, когда это необходимо.

В состав монорепозитория входят:

- `runtime/` — backend на FastAPI;
- `core/CORE/` — ядро знаний, Pulse, World Engine, RAG, граф знаний, визуальный контур;
- `core/KNOWLEDGE/`, `core/GENOME/`, `core/CHROMA_DB/` — данные, геном книги и векторная база;
- `arkaim-web/` — legacy-фронтенд Next.js;
- `arkaim-web-v2/` — новый фронтенд Next.js;
- `arkaim-mobile/` — заготовка мобильного приложения React Native/Expo;
- `docs/` — документация, ADR, планы этапов и аудиты;
- `SCHEMAS/` — JSON Schema;
- `runtime/tests/` и другие test-каталоги — автоматические проверки;
- `scripts/` — пайплайны, утилиты и обслуживающие скрипты;
- Docker, GitHub Actions, pre-commit и Makefile — эксплуатационная инфраструктура.

### 1.2. Цель аудита

Цель — определить, что проект из себя представляет сейчас, какие характеристики подтверждены, где находится граница между рабочей функцией и документальным заявлением, какие проблемы мешают развитию и какой следующий этап даст наибольшую ценность владельцу.

## 4. Архитектурная карта

```text
Читатель
   │
   ▼
Web UI: arkaim-web или arkaim-web-v2
   │  HTTP / WebSocket / SSE
   ▼
API proxy / FastAPI :8642
   │
   ├── auth: JWT, OAuth, API keys, RBAC
   │
   ├── BookPulse
   │     ├── KnowledgeLayer
   │     ├── ExpansionLayer
   │     ├── MeaningLayer
   │     ├── IdentityLayer
   │     ├── MissionLayer
   │     ├── WorldEngineLayer
   │     └── другие слои Pulse
   │
   ├── BookVoice
   │     └── LLM как голос: GigaChat / OpenRouter
   │
   ├── ReaderMemory
   ├── World Engine
   ├── Temporal World Model
   ├── Knowledge Graph
   ├── RAG / ChromaDB
   │
   └── Visual / Film Studio
           └── MediaPlan → внешний исполнитель → assets
```

### 4.1. Главный поток вопроса

1. Читатель отправляет вопрос через UI.
2. Frontend передаёт запрос backend.
3. Backend проверяет авторизацию и определяет пользователя.
4. Pulse ищет ответ в своих слоях.
5. При наличии факта ответ может быть сформирован без LLM.
6. При низкой уверенности BookVoice формулирует текст.
7. IdentityLayer выполняет финальную проверку.
8. Пользователь получает ответ с источником и уровнем уверенности.

### 4.2. Поток визуализации

```text
Запрос сцены
  → VisualContextBuilder
  → SceneContext
  → MediaPlan
  → MediaClient / внешний исполнитель
  → ComfyUI или Mock-провайдер
  → AssetStorage
  → файл и метаданные ассета
```

Главное архитектурное правило: смысловая модель книги не должна зависеть от деталей ComfyUI. Конкретный workflow, checkpoint и параметры генератора не должны проникать в доменную логику Pulse.

## 5. Функциональные характеристики

### 5.1. Ядро знаний

- хранение фактов, тем, цитат, сущностей и связей;
- RAG и поиск по книге;
- Knowledge Graph с обходом графа и поиском путей;
- World Engine как вычислиемая модель мира;
- temporal-модель с эпохами, настоящим и сценариями будущего;
- расширение знаний через пайплайны;
- provenance — происхождение и категория достоверности данных;
- геном книги и контролируемая эволюция.

### 5.2. Персонализация чтения

- профиль читателя;
- память читателя в SQLite;
- адаптация глубины и формы ответа;
- Presence — наблюдение за активностью и предложения автору;
- ReaderMemory и рекомендации;
- адаптивные ответы без передачи всей личности книги в LLM.

### 5.3. Веб-интерфейс

Legacy-фронтенд содержит страницы чтения, библиотеки, вопросов книге, настроек и другие разделы. Новый фронтенд `arkaim-web-v2` развивается как отдельная реализация с typed-контрактами, RBAC, realtime-компонентами и E2E-проверками.

### 5.4. Визуальный контур

- построение сцен и визуального контекста;
- MediaPlan как доменное описание намерения;
- поддержка image/video/mock/SVG сценариев;
- хранение ассетов и метаданных;
- Film Studio и сборка сцен;
- подключение ComfyUI через media boundary.

### 5.5. API и интеграции

- REST API для книги, мира, визуализации и администрирования;
- OpenAI-compatible endpoints `/v1/models` и `/v1/chat/completions`;
- `/providers/health`;
- OAuth Telegram/Google;
- API-ключи и JWT;
- WebSocket и SSE для событий;
- интеграция с внешним Media-проектом по контракту.

- расхождения API-контрактов;
- двойного исправления одной ошибки;
- разных UX-решений;
- неясного места новой функциональности;
- дублирования тестов и документации.

До удаления legacy необходимо формально подтвердить паритет функций и миграцию пользовательских сценариев.

### 9.2. Что считать результатом

Корректный результат теста должен содержать:

1. Команду запуска;
2. Окружение и версии;
3. Число тестов;
4. Число passed/failed/skipped;
5. Причины падений;
6. Подтверждение, что падение существовало до изменения.

Наличие большого числа тестов само по себе не означает, что весь продукт работает end-to-end.

### 9.3. Известный тип риска

В документации фиксируются проблемы с импортом `runtime.core` в части asset-тестов, а также mtime-flaky тест. Это похоже на проблемы тестовой среды, но перед исправлением нужно воспроизвести конкретный сбой и проверить, что он не скрывает реальную ошибку приложения.

## 11. Технический долг

Технический долг делится на три группы.

### 11.1. Долг, который нельзя исправлять без отдельного решения

- `GenerationParams.quality`, если поле признано мёртвым;
- legacy prompt projection, если его вывод является замороженным контрактом;
- seed-hash поведение, если оно специально сохранено;
- удаление legacy-фронтенда до подтверждения паритета;
- перенос queue/async/batch/regenerate без продуктового и архитектурного решения;
- изменение MediaPlan, SceneContext, temporal-контрактов без owner-GO.

### 11.2. Долг, который можно чистить отдельным узким milestone

- мёртвые imports;
- устаревшие комментарии;
- дублирующие словари;
- висящие `__all__`-экспорты;
- временные файлы и runtime-базы;
- устаревшая документация;
- неиспользуемые поля и провайдерские остатки.

### 11.3. Правило

Каждый пункт долга должен иметь ID, владельца, причину, критерий завершения и отдельный тест. Нельзя чинить долг «попутно» внутри продуктовой задачи.

1. **Понятная идея:** LLM не является источником истины, а книга остаётся первичным источником.

6. **Визуальный контур:** сценарий, план, внешний исполнитель и ассеты разделены.
7. **Есть история решений:** ADR, планы этапов, отчёты аудита и closure-документы.
8. **Инфраструктура разработки:** Docker, CI, pre-commit, health-check и скрипты.
9. **Тщательная фиксация статусов:** документы используют CLOSED/ACCEPTED/DEFERRED, что лучше, чем просто «готово».
10. **Проверяемая эволюция:** изменения снабжены коммитами, тестами и контрактными проверками.

- изменить замороженный контракт;
- принять наличие функции за её работоспособность;
- запустить новый параллельный pipeline вместо существующего.

### 13.3. Риск для качества

- runtime-команды зависят от локальных `.env` и внешних сервисов;
- часть тестов зависит от способа запуска;
- часть документации основана на снимке конкретного HEAD;
- внешний ComfyUI может быть доступен локально, но отсутствовать в другой среде.

## 14. Развитие продукта: рекомендуемое направление

### 14.1. Не расширять систему до подтверждения MVP

Следующая работа должна быть не «ещё один модуль», а доказательство основного пользовательского цикла:

```text
Читатель открывает книгу
  → задаёт вопрос
  → получает ответ
  → видит источник и уверенность
  → исследует связанную сущность/тему
  → при необходимости создаёт визуальный запрос
  → получает результат
  → возвращается к чтению или истории
```

### 14.2. Минимальный MVP Arkaim v2

MVP должен зафиксировать:

- кто является пользователем;
- что считается успешным ответом;
- какие слои Pulse обязаны ответить без LLM;
- как отображается provenance;
- что делать при низкой уверенности;
- какие роли и права существуют;
- какие экраны являются обязательными;
- что происходит при недоступности ComfyUI;
- какой пользовательский сценарий не входит в MVP.

### 14.3. Приоритеты

**P0 — доказать целостность:**

1. выбрать один главный сценарий;
2. провести его на чистом локальном запуске;
3. проверить backend, UI, контракты, auth и persistence;
4. зафиксировать результат в acceptance-критериях;
5. обновить source-of-truth документацию.

**P1 — убрать неопределённость:**

1. решить судьбу `arkaim-web`;
2. определить, что входит в MVP из Film Studio, temporal и community;
3. отделить обязательные функции от экспериментальных;
4. очистить runtime-артефакты;
5. закрыть или явно отложить известный test-debt.

**P2 — развивать после acceptance:**

- video;
- audio;
- mobile;
- i18n;
- production hardening;
- расширенная аналитика;
- дополнительные LLM-провайдеры;
- сложные очереди и batch-операции.

## 15. Порядок следующих milestone

### Milestone 1: Product Definition

**Цель:** определить минимальный пользовательский цикл.

**Результат:**

- один сценарий;
- acceptance criteria;
- список экранов;
- список API;
- список проверяемых данных;
- explicit non-goals.

**Не делать:** не писать новый код до утверждения сценария.

### Milestone 2: End-to-End Proof

**Цель:** запустить сценарий на чистом локальном окружении.

**Результат:**

- backend доступен;
- frontend открывается;
- auth работает;
- вопрос доходит до Pulse;
- LLM вызывается только при предусмотренном низком уровне уверенности;
- ответ содержит provenance;
- визуальный маршрут или его явная заглушка работает;
- состояние сохраняется.

### Milestone 3: Source-of-Truth Consolidation

**Цель:** убрать противоречия в документации.

**Результат:**

- один документ с текущими метриками;
- актуальные ADR-пути;
- актуальные статусы;
- актуальные команды запуска и тестирования;
- один список известных долгов.

### Milestone 4: Frontend Decision

**Цель:** решить, что является каноническим UI.

**Варианты:**

- продолжить развитие v2 и затем удалить legacy;
- временно поддерживать оба, но запретить новые функции в legacy;
- выбрать legacy как канонический и не развивать v2.

Третий вариант допустим только после отдельного сравнительного аудита, поскольку v2 уже содержит typed contracts и новые закрытые F-этапы.

### Milestone 5: Debt and Operations

**Цель:** сделать состояние репозитория предсказуемым.

- runtime-файлы в `.gitignore` или явно исключены;
- база проверяется отдельной процедурой;
- test fixtures не зависят от локальных абсолютных путей;
- удалены мёртвые импорты и комментарии;
- CI стабильно повторяет локальные проверки.

## 18. Итоговая оценка

### Простыми словами

Проект «Наследие Аркаима» — не пустой эксперимент, а большая система с отдельным ядром знаний, backend, двумя веб-интерфейсами, визуальным контуром, тестами и документацией. Главная идея проекта зафиксирована хорошо: книга остаётся источником истины, а LLM — голосом.

Но проект пока нельзя безопасно назвать полностью готовым продуктом. В репозитории есть признаки незавершённости: устаревшие документы, два фронтенда, отложенные долги, runtime-артефакты и неопределённый минимальный пользовательский сценарий. Самая полезная следующая работа — не расширение количества функций, а проверка и принятие одного полного пути пользователя.
