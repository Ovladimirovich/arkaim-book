# ARKAIM — РЕЖИМ САМОСТОЯТЕЛЬНОЙ РАЗРАБОТКИ ИНЖЕНЕРА

## Главный принцип

Инженер самостоятельно доводит поставленную задачу до рабочего состояния.

OWNER задаёт:

* цель;
* архитектурные границы;
* уже принятые решения;
* STOP GATE / OWNER-GO там, где действительно требуется решение владельца.

Инженер НЕ должен перекладывать на OWNER технические решения, которые можно принять самостоятельно на основании существующего кода, документации, тестов и архитектурных контрактов.

---

## 1. Перед началом задачи

Самостоятельно:

1. Изучи актуальный `docs/ARKAIM_KNOWLEDGE_DEVELOPMENT_PLAN.md`.
2. Проверь связанные архитектурные документы.
3. Изучи фактический код и существующие тесты.
4. Определи текущую точку реализации.
5. Определи зависимости и существующие механизмы, которые нужно переиспользовать.
6. Сформулируй минимальный implementation scope.
7. Проверь, нет ли уже существующего решения, которое можно расширить вместо создания нового.

Не спрашивай OWNER о том, что уже следует из существующих документов или фактического состояния проекта.

---

## 2. Во время реализации

Работай самостоятельно от начала до конца:

**inspect → design locally → implement → test → diagnose → fix → retest → integrate → verify.**

Если обнаружена проблема:

* сначала самостоятельно исследуй её;
* найди причину;
* исправь;
* повторно запусти проверки.

Не останавливайся после обнаружения первой ошибки с вопросом «что делать дальше?».

Если первоначальный технический подход оказался неправильным — самостоятельно измени подход, сохранив архитектурные ограничения.

---

## 3. Технические решения

Самостоятельно принимай решения по:

* структуре кода;
* выбору существующих extension points;
* repository/resolver implementation;
* внутренним helper/API;
* обработке ошибок;
* тестовой структуре;
* совместимости;
* refactoring, необходимому для выполнения задачи;
* выбору между несколькими техническими реализациями.

Выбирай решение, которое:

1. соответствует утверждённой архитектуре;
2. минимально меняет существующее поведение;
3. переиспользует существующий код;
4. сохраняет backward compatibility;
5. имеет проверяемое тестами поведение.

Не выноси такие решения на OWNER только потому, что существует несколько технических вариантов.

---

## 4. Когда ОБЯЗАТЕЛЬНО остановиться и спросить OWNER

Останавливайся только если требуется новое архитектурное или продуктово-смысловое решение, которого нет в утверждённых документах.

Например:

* изменение уже принятого canonical contract;
* изменение утверждённой provenance semantics;
* изменение границы WorldModel / Temporal / crosswalk;
* изменение публичного API contract;
* изменение принятой persistence policy;
* необходимость нарушить установленную compatibility policy;
* появление нескольких вариантов, которые имеют разные продуктовые/архитектурные последствия и не разрешаются существующими правилами.

Во всех остальных случаях — решай самостоятельно.

---

## 5. Не путать STOP GATE с технической паузой

STOP GATE означает:

> требуется решение OWNER.

Он НЕ означает:

> инженер закончил писать код и ждёт дальнейших инструкций.

До STOP GATE инженер должен самостоятельно выполнить весь разрешённый scope, включая:

* код;
* integration;
* tests;
* regression checks;
* диагностику;
* исправления;
* документацию;
* verification.

Если STOP GATE не достигнут — продолжай работу.

---

## 6. Не останавливаться на «минимально реализовано»

Если задача требует integration, результатом должна быть работающая integration.

Нельзя считать задачу завершённой формулировками:

* «модель создана»;
* «каркас добавлен»;
* «можно продолжить позже»;
* «основная часть готова».

Нужно довести изменение до состояния:

**код существует → подключён → реально используется → проверен → существующее поведение не сломано.**

Если обнаружены необходимые мелкие изменения в соседнем коде для завершения задачи — внеси их самостоятельно, если они находятся внутри утверждённого scope.

---

## 7. Тестирование

После реализации:

1. Запусти targeted tests.
2. Запусти связанные regression tests.
3. Если изменение затрагивает общий контракт — запусти соответствующий более широкий набор.
4. Исправь найденные проблемы.
5. Повтори тесты после исправлений.

Не сообщай «готово» только потому, что код компилируется.

Фактическое состояние должно быть проверено.

---

## 8. Если тесты или окружение ломаются

Не останавливайся сразу.

Сначала самостоятельно установи:

* ошибка в реализации;
* ошибка существующего кода;
* устаревший тест;
* проблема окружения;
* отсутствующая зависимость;
* конфликт с legacy behavior.

Если проблема относится к текущей задаче — исправь её.

Если проблема внешняя и действительно блокирует работу — зафиксируй точную причину и минимально необходимое решение.

---

## 9. Документация

После завершения implementation:

* обнови документацию, если фактическое состояние изменилось;
* не создавай новую архитектуру задним числом;
* не переписывай стратегический документ ради косметики;
* зафиксируй только фактически реализованное состояние.

---

## 10. Git

Инженер самостоятельно отвечает за Git hygiene:

* проверяет diff;
* проверяет изменённые файлы;
* убеждается, что нет случайных изменений;
* сохраняет результат согласно принятому workflow проекта.

OWNER не должен вручную контролировать каждый Git-шаг.

---

## 11. Отчёт OWNER

В конце задачи дай короткий отчёт:

### DONE

Что реально реализовано.

### VERIFIED

Какие проверки выполнены и результат.

### PROBLEMS

Только реальные оставшиеся проблемы.

### STOP GATE

* `CLOSED` — если задача полностью завершена и следующий шаг разрешён;
* `OPEN` — если требуется OWNER decision.

### NEXT

Самостоятельно определи:

* ближайшую следующую конкретную задачу;
* дальнейшее направление разработки.

Но **не начинай следующий milestone автоматически**, если для него требуется новый OWNER-GO.

---

## 12. Главное правило самостоятельности

Не задавай OWNER вопрос:

> «Что мне делать дальше?»

если ответ можно получить из:

* `ARKAIM_KNOWLEDGE_DEVELOPMENT_PLAN.md`;
* существующей архитектуры;
* фактического кода;
* тестов;
* уже принятых OWNER decisions.

Вместо этого:

**сам определи следующий технический шаг, выполни его и доведи до проверенного состояния.**

OWNER должен принимать только те решения, которые действительно принадлежат OWNER.
